1. Overview

This guide is written against the actual MyKidsSpendingAndroid project (/Odin Projects/MyKidsSpendingAndroid, package com.odininc.mykidsspending) — not generic Android boilerplate. That app is 100% Java, Activity-per-screen (no Jetpack Compose, no ViewModel/ Room), with a base MKSDelegate extends Activity class, a CoreData singleton for in-memory session state, and all networking done by hand via HttpURLConnection dispatched through AppExecutors. There is currently no FCM/notification code in the project at all — this guide adds it from scratch, on top of the Firebase integration that already exists for Crashlytics.

Backend Contract (Bifrost)

The backend side is already built and app-agnostic — nothing here needs to change for Android:

EndpointMethodBodyPurpose
api/RegisterNotificationDevicePOST{ uid, fcm_token }Registers/confirms a device's FCM token for a uid. Idempotent.
api/Admin/TestSendFcmPOST{ uid?, token?, title?, body? }Sends a real test push without needing a real order — see Testing.
Tip: uid is either a parent account uid (MKSdata.security.uid) or a student's own uid (MKSdata.student.uid). It is not a device id.

Actual push delivery happens server-side: UpdateOrdersController.NotifyOrderStatusChange resolves the relevant uid(s) for an order, looks up every registered fcm_token for those uids via notification_device, and sends through FcmSender (HTTP v1 API, MKS App's own Firebase project — mykidsspending-e29cd, the same project this Android app's google-services.json already points to).

2. Firebase Setup

Most of this is already done. app/google-services.json already exists and points at MKS App's Firebase project (mykidsspending-e29cd, the same project the iOS app uses) — it currently only backs Crashlytics (app/build.gradle already applies com.google.firebase.crashlytics and pulls in firebase-bom). The only change needed is adding the messaging artifact to the existing BOM dependency block:

// app/build.gradle
dependencies {
    implementation platform('com.google.firebase:firebase-bom:34.9.0') // already present
    implementation 'com.google.firebase:firebase-crashlytics'          // already present
    implementation 'com.google.firebase:firebase-messaging'            // add this line
}
Tip: No new console setup, no new google-services.json download — the existing file already registers this app's package (com.odininc.mykidsspending) under the right Firebase project.

3. AndroidManifest.xml

Add the service next to the existing TouchService declaration, and the notification permission next to the existing INTERNET/WRITE_SETTINGS permissions:

<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.WRITE_SETTINGS"/>
<!-- Required on API 33+ to actually display notifications -->
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />

<application>
    ...
    <service android:name="com.odininc.mykidsspending.Service.TouchService" ... /> <!-- existing -->

    <service
        android:name="com.odininc.mykidsspending.Service.MksFirebaseMessagingService"
        android:exported="false">
        <intent-filter>
            <action android:name="com.google.firebase.MESSAGING_EVENT" />
        </intent-filter>
    </service>
</application>

4. MksFirebaseMessagingService

New file: app/src/main/java/com/odininc/mykidsspending/Service/MksFirebaseMessagingService.java. Owns both token capture and message display, mirroring NotificationsService.swift on iOS. Logging follows MKSDelegate's existing dual pattern (Logcat + Crashlytics) rather than introducing a new logging utility.

onNewToken

package com.odininc.mykidsspending.Service;

import android.util.Log;
import com.google.firebase.crashlytics.FirebaseCrashlytics;
import com.google.firebase.messaging.FirebaseMessagingService;
import com.google.firebase.messaging.RemoteMessage;

public class MksFirebaseMessagingService extends FirebaseMessagingService {

    private static final String TAG = "FCM";

    @Override
    public void onNewToken(String token) {
        super.onNewToken(token);
        Log.i(TAG, "New FCM token received");
        FirebaseCrashlytics.getInstance().log("FCM: new token received");
        // Cache + attempt registration immediately; see section 5 for the actual call.
        NotificationRegistrar.onTokenReceived(getApplicationContext(), token);
    }
Tip: onNewToken can fire more than once per install (token rotation, app restore, etc.) — always re-register on every call, same as iOS re-registers on every didReceiveRegistrationToken call.

Notification Channel (API 26+)

Android requires a NotificationChannel before any notification can display on API 26+ (this app's minSdkVersion is 24, so the version check below is required, not optional). Create it lazily the first time a message arrives:

    private static final String CHANNEL_ID = "order_updates";

    private void ensureChannel() {
        if (android.os.Build.VERSION.SDK_INT < android.os.Build.VERSION_CODES.O) return;
        NotificationManager manager = getSystemService(NotificationManager.class);
        if (manager.getNotificationChannel(CHANNEL_ID) == null) {
            NotificationChannel channel = new NotificationChannel(
                    CHANNEL_ID, "Order Updates", NotificationManager.IMPORTANCE_HIGH);
            manager.createNotificationChannel(channel);
        }
    }

onMessageReceived

Bifrost's FcmSender currently sends a notification-type payload (title + body, no custom data block) — see Gotchas for what that means for foreground vs background delivery.

    @Override
    public void onMessageReceived(RemoteMessage message) {
        super.onMessageReceived(message);
        ensureChannel();

        String title = message.getNotification() != null ? message.getNotification().getTitle() : "Notification";
        String body = message.getNotification() != null ? message.getNotification().getBody() : "";

        NotificationCompat.Builder builder = new NotificationCompat.Builder(getApplicationContext(), CHANNEL_ID)
                .setSmallIcon(R.drawable.ic_notification)
                .setContentTitle(title)
                .setContentText(body)
                .setAutoCancel(true)
                .setPriority(NotificationCompat.PRIORITY_HIGH);

        NotificationManagerCompat.from(getApplicationContext())
                .notify((int) System.currentTimeMillis(), builder.build());
    }
}

Runtime Permission (API 33+)

On Android 13+ (this app targets API 35), notifications require the runtime POST_NOTIFICATIONS permission (parallel to iOS's requestAuthorization). Request it from MainActivity, ideally right after login rather than at cold launch:

if (android.os.Build.VERSION.SDK_INT >= android.os.Build.VERSION_CODES.TIRAMISU &&
        ContextCompat.checkSelfPermission(this, Manifest.permission.POST_NOTIFICATIONS)
                != PackageManager.PERMISSION_GRANTED) {
    ActivityCompat.requestPermissions(this,
            new String[]{Manifest.permission.POST_NOTIFICATIONS}, REQUEST_CODE_NOTIFICATIONS);
}

5. Registering the Token with Bifrost

Endpoints.java

Add the new endpoint next to the other Bifrost mobile endpoints (same BASE env-switchable constant used by FULL_BALANCE2/RCV_TRAN, not the always-live BASE_LIVE used by the Trifrost endpoints):

// Endpoints.java
public static final String REGISTER_NOTIFICATION_DEVICE = BASE + "/Bifrost/api/RegisterNotificationDevice";

NotificationRegistrar

New file: app/src/main/java/com/odininc/mykidsspending/Service/NotificationRegistrar.java. Follows the exact networking pattern already used in MainActivity (HttpURLConnection, dispatched via AppExecutors.runOnBackground), and dedups via SecurePrefs the same way iOS caches the last-sent uid|fcm_token pair in UserDefaults.

package com.odininc.mykidsspending.Service;

import android.content.Context;
import android.content.SharedPreferences;
import android.util.Log;

import com.odininc.mykidsspending.AppExecutors;
import com.odininc.mykidsspending.Data.CoreData;
import com.odininc.mykidsspending.SecurePrefs;
import com.odininc.mykidsspending.util.Endpoints;

import org.json.JSONObject;

import java.io.OutputStream;
import java.net.HttpURLConnection;
import java.net.URL;
import java.util.HashSet;
import java.util.Set;

public final class NotificationRegistrar {

    private static final String TAG = "FCM";
    private static final String KEY_REGISTERED_PAIRS = "FCM_REGISTERED_UID_TOKEN_PAIRS";

    private static volatile String latestToken;

    private NotificationRegistrar() { }

    public static void onTokenReceived(Context context, String token) {
        latestToken = token;
        registerIfUidKnown(context);
    }

    /** Call this once CoreData.uidpayer is populated (see "When to Call It" below). */
    public static void registerIfUidKnown(Context context) {
        String token = latestToken;
        String uid = CoreData.getInstance().uidpayer;
        if (token == null || token.isEmpty() || uid == null || uid.isEmpty()) {
            Log.i(TAG, "RegisterNotificationDevice skipped: uid or token not available yet");
            return;
        }

        String dedupKey = uid + "|" + token;
        SharedPreferences prefs = SecurePrefs.get(context.getApplicationContext());
        Set<String> alreadySent = prefs.getStringSet(KEY_REGISTERED_PAIRS, new HashSet<>());
        if (alreadySent.contains(dedupKey)) {
            Log.i(TAG, "RegisterNotificationDevice skipped: already registered for this uid/token");
            return;
        }

        AppExecutors.runOnBackground(() -> {
            boolean success = post(uid, token);
            if (success) {
                Set<String> updated = new HashSet<>(alreadySent);
                updated.add(dedupKey);
                prefs.edit().putStringSet(KEY_REGISTERED_PAIRS, updated).apply();
                Log.i(TAG, "RegisterNotificationDevice succeeded");
            } else {
                Log.i(TAG, "RegisterNotificationDevice failed");
            }
        });
    }

    private static boolean post(String uid, String token) {
        HttpURLConnection conn = null;
        try {
            URL url = new URL(Endpoints.REGISTER_NOTIFICATION_DEVICE);
            conn = (HttpURLConnection) url.openConnection();
            conn.setRequestMethod("POST");
            conn.setRequestProperty("Content-Type", "application/json; charset=utf-8");
            conn.setDoOutput(true);

            JSONObject payload = new JSONObject();
            payload.put("uid", uid);
            payload.put("fcm_token", token);

            try (OutputStream os = conn.getOutputStream()) {
                os.write(payload.toString().getBytes("UTF-8"));
            }

            int code = conn.getResponseCode();
            return code >= 200 && code < 300;
        } catch (Exception e) {
            Log.e(TAG, "RegisterNotificationDevice exception", e);
            return false;
        } finally {
            if (conn != null) conn.disconnect();
        }
    }
}

When to Call It

Note: This registers CoreData.getInstance().uidpayer — the parent uid. That's a deliberate difference from the current iOS implementation, which was changed to register student uids only (parent registration was removed as redundant, since UpdateOrdersController already resolves each order's notification via the specific student's own uid). CoreData doesn't currently expose a clean per-student uid list the way iOS's childAccountArray does (see Gotchas) — registering uidpayer is the pragmatic first step until CoreData/the login-parsing code is extended to track student uids individually.

Call NotificationRegistrar.registerIfUidKnown(context) at every point uidpayer becomes known or changes, not just once:

  • Right where data.uidpayer gets set today, in MainActivity.fetchAccessTokenAndHomeThemeTrifrost — immediately after the existing if (uid != null && !uid.isEmpty() && ...) data.uidpayer = uid; block.
  • After any silent/auto re-login on app relaunch.
Learned the hard way on iOS: the very first registration attempt (from onNewToken, which typically fires at cold start) will almost always run before login finishes and uidpayer is set. Don't treat that as a failure — it's expected, and is exactly why registerIfUidKnown is also called explicitly at the login success site. See Gotchas for the deeper pitfall this exposed on iOS.

6. Testing

No real order is required to test delivery. Use the admin endpoint added alongside this feature:

curl -X POST http://54.167.168.76/Bifrost/api/Admin/TestSendFcm \
  -H "Content-Type: application/json" \
  -d '{"token": "<paste the FCM token from Logcat here>", "title": "Hi", "body": "Test push"}'

# or by uid, sending to every token registered for it:
curl -X POST http://54.167.168.76/Bifrost/api/Admin/TestSendFcm \
  -H "Content-Type: application/json" \
  -d '{"uid": "<uidpayer value>"}'

The response includes a per-token {token, success, error, messageId} so you can see exactly what FCM said, without needing DB access.

Tip: Grab the current device's FCM token from Logcat — the Log.i(TAG, "New FCM token received") line in onNewToken only logs that a token arrived, not its value; temporarily log token itself during development.

7. Gotchas & Lessons Learned

IssueDetails
No clean per-student uid list CoreData.loginDataMap is a raw HashMap<String,Object> with no typed student/uid accessor (multi-student data is stitched together ad hoc from it and schoolshashMap). Unlike iOS's childAccountArray, there's no drop-in equivalent to iterate for per-student registration today. This guide registers uidpayer (parent) as a pragmatic first step — extending CoreData's login parsing to also capture a typed list of student uids is a real follow-up if Android needs full parity with iOS's student-level registration.
Foreground vs background delivery Because Bifrost sends a notification-type payload (not data-only), Android's FCM SDK auto-displays it via the system tray whenever the app is backgrounded or killed — onMessageReceived() is not called in that case. It only fires when the app is in the foreground. Test both states; a push that "does nothing" while the app is open is often working correctly and just needs the foreground display code in section 4.
Token arrives before login onNewToken typically fires at cold start, before uidpayer is set. On iOS this caused registration to silently no-op forever, because a leftover bug let a stale/placeholder app-state singleton get read instead of the real one populated by login — don't assume "no uid yet" always means "waiting for login"; keep the two cases distinguishable in logs so a similar bug doesn't hide behind an expected-looking log line on Android.
Emulators need Google Play FCM requires Google Play Services. Use an emulator image with the Play Store (not a bare AOSP image), or a physical device.
Notification channel required (API 26+) Notifications silently fail to display (no crash) if the channel was never created before notify() is called. minSdkVersion is 24 here, so the version check is load-bearing, not defensive boilerplate.
POST_NOTIFICATIONS permission (API 33+) Without it, onMessageReceived still fires and your code runs, but NotificationManagerCompat.notify() silently does nothing. targetSdkVersion is 35 here, so this applies.
