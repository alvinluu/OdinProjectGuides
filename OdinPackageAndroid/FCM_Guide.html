1. Overview

Firebase Cloud Messaging (FCM) delivers push notifications to a device via a per-install registration token. Odin's MKS iOS app already implements this end-to-end (Firebase SPM package → MessagingDelegate → register token with Bifrost → Bifrost's FcmSender pushes on order status changes). This guide documents the equivalent Android implementation, targeting a Kotlin app built alongside OdinPackageAndroid (or using it directly, once an Android FCM helper is added to that package).

Backend Contract (Bifrost)

The backend side is already built and app-agnostic — nothing here needs to change for Android:

EndpointMethodBodyPurpose
api/RegisterNotificationDevicePOST{ uid, fcm_token }Registers/confirms a device's FCM token for a uid. Idempotent.
api/Admin/TestSendFcmPOST{ uid?, token?, title?, body? }Sends a real test push without needing a real order — see Testing.
Tip: uid is either a parent account uid (MKSdata.security.uid) or a student's own uid (MKSdata.student.uid) — whatever uid concept your app's login uses. It is not a device id.

Actual push delivery happens server-side: UpdateOrdersController.NotifyOrderStatusChange resolves the relevant uid(s) for an order, looks up every registered fcm_token for those uids via notification_device, and sends through FcmSender (HTTP v1 API, one Firebase project per Odin app — e.g. MKS App's Firebase project is separate from the POS app's).

2. Firebase Project Setup

Console + google-services.json

1 In the Firebase console, open the same Firebase project the corresponding iOS app uses (e.g. MKS App's project) — or create a new Android app entry under it if one doesn't exist. Use the app's real applicationId as the Android package name.
2 Download google-services.json and place it in the app module's root (next to build.gradle.kts), same as GoogleService-Info.plist sits at the iOS project root.
Note: Each Odin app has its own Firebase project (MKS App, POS app, Attendance app, etc. all differ) — don't reuse one app's google-services.json for another.

Gradle

// project-level build.gradle.kts
plugins {
    id("com.google.gms.google-services") version "4.4.2" apply false
}

// app/build.gradle.kts
plugins {
    id("com.google.gms.google-services")
}

dependencies {
    implementation(platform("com.google.firebase:firebase-bom:33.5.1"))
    implementation("com.google.firebase:firebase-messaging")
}

4. FirebaseMessagingService

Create one subclass per app (mirrors NotificationsService.swift on iOS — owns both token capture and message display).

onNewToken

class OdinFirebaseMessagingService : FirebaseMessagingService() {

    override fun onNewToken(token: String) {
        super.onNewToken(token)
        // Cache + attempt registration immediately; see section 5 for the actual call.
        NotificationRegistrar.onTokenReceived(applicationContext, token)
    }
Tip: onNewToken can fire more than once per install (token rotation, app restore, etc.) — always re-register on every call, same as iOS re-registers on every didReceiveRegistrationToken call.

Notification Channel (API 26+)

Android requires a NotificationChannel before any notification can display on API 26+. Create it once, e.g. in Application.onCreate() or lazily the first time a message arrives:

private fun ensureChannel(context: Context) {
    if (Build.VERSION.SDK_INT < Build.VERSION_CODES.O) return
    val manager = context.getSystemService(NotificationManager::class.java)
    if (manager.getNotificationChannel(CHANNEL_ID) == null) {
        val channel = NotificationChannel(
            CHANNEL_ID,
            "Order Updates",
            NotificationManager.IMPORTANCE_HIGH
        )
        manager.createNotificationChannel(channel)
    }
}

companion object {
    const val CHANNEL_ID = "order_updates"
}

onMessageReceived

Bifrost's FcmSender currently sends a notification-type payload (title + body, no custom data block) — see Gotchas for what that means for foreground vs background delivery.

    override fun onMessageReceived(message: RemoteMessage) {
        super.onMessageReceived(message)
        ensureChannel(applicationContext)

        val title = message.notification?.title ?: "Notification"
        val body = message.notification?.body ?: ""

        val notification = NotificationCompat.Builder(applicationContext, CHANNEL_ID)
            .setSmallIcon(R.drawable.ic_notification)
            .setContentTitle(title)
            .setContentText(body)
            .setAutoCancel(true)
            .setPriority(NotificationCompat.PRIORITY_HIGH)
            .build()

        NotificationManagerCompat.from(applicationContext)
            .notify(System.currentTimeMillis().toInt(), notification)
    }
}

Runtime Permission (API 33+)

On Android 13+, notifications require the runtime POST_NOTIFICATIONS permission (parallel to iOS's requestAuthorization). Request it from an Activity, ideally right after login rather than at cold launch:

if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU &&
    ContextCompat.checkSelfPermission(this, Manifest.permission.POST_NOTIFICATIONS)
        != PackageManager.PERMISSION_GRANTED) {
    requestPermissions(arrayOf(Manifest.permission.POST_NOTIFICATIONS), REQUEST_CODE_NOTIFICATIONS)
}

5. Registering the Token with Bifrost

Kotlin Implementation

Follow the same networking style as PortableLog (plain HttpURLConnection + JSONObject, no external HTTP library), and the same dedup approach iOS landed on: cache the last successfully-registered uid|fcm_token pair and skip re-sending until either changes.

object NotificationRegistrar {

    private const val PREFS_NAME = "odin_notification_registrar"
    private const val KEY_REGISTERED = "registered_uid_token_pairs"

    private val scope = CoroutineScope(Dispatchers.IO + SupervisorJob())
    private var latestToken: String? = null

    fun onTokenReceived(context: Context, token: String) {
        latestToken = token
        registerForKnownUids(context, token)
    }

    /** Call this once your app knows the logged-in student uid(s) — e.g. right after login. */
    fun onUidsAvailable(context: Context, uids: List) {
        val token = latestToken ?: return
        registerUids(context, uids, token)
    }

    private fun registerForKnownUids(context: Context, token: String) {
        val uids = YourSessionStore.currentStudentUids(context) // however your app tracks logged-in uids
        if (uids.isNotEmpty()) registerUids(context, uids, token)
    }

    private fun registerUids(context: Context, uids: List, token: String) {
        val prefs = context.getSharedPreferences(PREFS_NAME, Context.MODE_PRIVATE)
        val alreadySent = prefs.getStringSet(KEY_REGISTERED, emptySet()) ?: emptySet()

        uids.forEach { uid ->
            val dedupKey = "$uid|$token"
            if (dedupKey in alreadySent) return@forEach

            scope.launch {
                val success = post(uid, token)
                if (success) {
                    prefs.edit()
                        .putStringSet(KEY_REGISTERED, alreadySent + dedupKey)
                        .apply()
                }
            }
        }
    }

    private suspend fun post(uid: String, token: String): Boolean = withContext(Dispatchers.IO) {
        try {
            val url = URL(BifrostEndpoints.Environment.LIVE.bifrostBase + "RegisterNotificationDevice")
            val conn = url.openConnection() as HttpURLConnection
            try {
                conn.requestMethod = "POST"
                conn.setRequestProperty("Content-Type", "application/json")
                conn.doOutput = true
                val payload = JSONObject().apply {
                    put("uid", uid)
                    put("fcm_token", token)
                }
                conn.outputStream.use { it.write(payload.toString().toByteArray()) }
                conn.responseCode in 200..299
            } finally {
                conn.disconnect()
            }
        } catch (e: Exception) {
            false
        }
    }
}

When to Call It

Note: Register student uids only — do not register a parent/account uid. This mirrors a deliberate decision made on the iOS side: UpdateOrdersController already resolves each order's notification via that specific student's own uid, so registering a parent uid is redundant and was removed entirely from the iOS implementation.

Call onUidsAvailable() at every point student uids become known or change, not just once:

  • Right after a successful login response is parsed (don't rely solely on the token-received callback — it usually fires before login completes, since FCM registers the token at app start).
  • After a silent/auto re-login on app relaunch.
  • After any student-selection change, if your app supports switching between multiple students on one device.
Learned the hard way on iOS: the very first registration attempt (from the token-received callback) will almost always fire before login finishes and student uids are known. Don't treat that as a failure — either poll/wait briefly for uids to appear, or simply rely on the explicit call at login success to actually register. See Gotchas for the deeper pitfall this exposed on iOS.

6. Testing

No real order is required to test delivery. Use the admin endpoint added alongside this feature:

curl -X POST http://54.167.168.76/Bifrost/api/Admin/TestSendFcm \
  -H "Content-Type: application/json" \
  -d '{"token": "<paste the FCM token from Logcat here>", "title": "Hi", "body": "Test push"}'

# or by uid, sending to every token registered for it:
curl -X POST http://54.167.168.76/Bifrost/api/Admin/TestSendFcm \
  -H "Content-Type: application/json" \
  -d '{"uid": "<student uid>"}'

The response includes a per-token {token, success, error, messageId} so you can see exactly what FCM said, without needing DB access.

Tip: Grab the current device's FCM token from Logcat — log it once in onNewToken during development (Log.d("FCM", "token=$token")).

7. Gotchas & Lessons Learned

IssueDetails
Foreground vs background delivery Because Bifrost sends a notification-type payload (not data-only), Android's FCM SDK auto-displays it via the system tray whenever the app is backgrounded or killed — onMessageReceived() is not called in that case. It only fires when the app is in the foreground. Test both states; a push that "does nothing" while the app is open in the emulator is often working correctly and just needs the foreground display code in section 4.
Token arrives before login onNewToken typically fires at cold start, before any uid is known. On iOS this caused registration to silently no-op forever, because a leftover bug let a stale/placeholder app-state singleton get read instead of the real one populated by login — don't assume "no uid yet" always means "waiting for login"; add logging that clearly distinguishes the two so a similar bug doesn't hide behind an expected-looking log line on Android.
Emulators need Google Play FCM requires Google Play Services. Use an emulator image with the Play Store (not a bare AOSP image), or a physical device.
Notification channel required (API 26+) Notifications silently fail to display (no crash) if the channel was never created before notify() is called.
POST_NOTIFICATIONS permission (API 33+) Without it, onMessageReceived still fires and your code runs, but NotificationManagerCompat.notify() silently does nothing.
Don't register the parent/account uid Only register student uids the device is associated with — see When to Call It.
