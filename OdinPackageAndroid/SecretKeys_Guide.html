1. The Endpoint

Bifrost exposes one endpoint that returns the current client keys. No login/auth required — it's meant to be callable before the user signs in.

EndpointMethodRequest body
api/MKSAppConfigPOST{ app, version, osversion } (optional, logging only)
POST /Bifrost/api/MKSAppConfig
{ "app": "MKS Android", "version": "1.0", "osversion": "14" }

# Response:
{
  "status": "1",
  "message": "",
  "data": {
    "encryptionKey": "<value>",
    "webserviceKey": "<value>",
    "transactionKey": "<value>"
  }
}
Tip: encryptionKey exists only for an iOS-specific feature (obfuscating the password in log lines). Only pull it out of the response if Android actually has a matching use for it — otherwise ignore that field.

2. When to Call It

1 At app launch: load whatever's already stored locally (see section 4) into memory. This is a local read — don't call the endpoint here, and don't block startup or the login screen on a network call.
2 If nothing's stored yet (fresh install, or storage was cleared): call the endpoint once in the background and save the result. The app can keep running with empty keys in the meantime.
3 Whenever a key turns out to be wrong (see section 5): call the endpoint again to get a fresh value.

Outside of those three situations, don't call it — the whole point is to avoid hitting the network every time a key is needed.

3. Encrypt Before Storing, Decrypt Before Using

These keys sign real financial requests (ACH/Google Pay) and the account barcode, so they shouldn't sit in plaintext on disk any more than a password would:

1 When the endpoint returns fresh values, encrypt them before writing to local storage.
2 When a key is actually needed to sign something, read the encrypted value and decrypt it in memory just before use. Don't keep the decrypted value around longer than the single operation that needs it.
Tip: Use whatever encrypted-storage mechanism the app already uses for the saved login password — don't build a separate encryption scheme just for these two keys. On modern Android that's typically androidx.security.crypto.EncryptedSharedPreferences, which encrypts values at rest automatically; if that's already in use elsewhere in the app, you may not need to write any manual encrypt/decrypt code at all — just read and write plain strings through it.

4. Storing and Using the Keys Locally

1 Store two values: the webservice key (ACH/Google Pay signing) and the transaction key (barcode signing).
2 Wherever the app currently signs an ACH/Google Pay request or the barcode payload, read the stored key at that point instead of using a hardcoded constant.
3 Treat "key is empty/missing" as "haven't fetched it yet" — not an error state that needs special handling beyond triggering a fetch (section 2, step 2).

5. If a Signed Operation Fails, Update the Keys

A key can go stale if it's rotated on the backend after the app already cached the old value. What "failure" looks like depends on what the key is used for:

1 Signing a request that gets a response (ACH, Google Pay): if the signed request is rejected, call the endpoint again, re-sign with the fresh key, and retry the request once. If it fails again, show the error normally — don't loop.
2 Signing the barcode: the barcode is verified on a separate device at checkout, not by any response the phone receives, so there's no failure to detect after the fact. The only thing to check is whether the stored key is empty before signing — if so, fetch first, then sign with whatever comes back.
Note: Don't retry more than once per attempt. If refreshing doesn't fix it, the problem is elsewhere (e.g. the key genuinely wasn't set on the backend yet) and retrying again won't help.
