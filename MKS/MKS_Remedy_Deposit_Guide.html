1. What is an errored deposit?

When a parent funds a student account (Apple Pay card deposit or ACH/eCheck), the gateway call can fail after the card may already have been charged — a dropped connection, a timeout, or a processing error. The attempt is recorded in fund.webtran with approval = ERROR and the gateway message saved in the reference field.

The danger case is simple to state:

The money may have left the parent's card, but the student's account was never credited. Those are the deposits that need a remedy.

Common reference messages you will see:

Error messageTypically means
The request timed out.Gateway reply was lost — charge may have gone through
The network connection was lost.Gateway reply was lost — charge may have gone through
An error occurred during processing. Please try again.Usually did not complete
There was an error processing the payment data. Unable to decrypt data.Failed before the charge — usually no money moved
User authentication failed due to invalid authentication values.Failed before the charge — usually no money moved

You do not have to judge these by the message alone — the dashboard checks each one against Authorize.net to find out what really happened.

2. How reconciliation works

For each errored deposit the dashboard lines up two independent facts:

  • Authorize.net — did the money actually move? The deposit's reference (WK + counter) is searched across settled batches (around the deposit date) and the unsettled list.
  • mksdata.transfer — was the student account actually credited? The deposit posts two rows (a Dep deposit and an Svc fee). A later void posts mirror rows with negated amounts, so a voided deposit nets back to zero.

The remedy verdict

Authorize.netAccount creditVerdictAction
Charged (settled or pending)Credited — liveOKNothing — they match
ChargedNot creditedNeeds remedyReplay the deposit (post the credit)
ChargedCredited then voidedNeeds remedyAccount is short — review / re-credit
No charge foundCredited — liveNeeds remedyVoid the deposit (no money backing it)
No charge foundNot creditedCleanNothing — the parent likely retried

3. Finding deposits that need remedy

1 Open AuthNet Dashboard and go to the Timed-out / Error (Remedy) screen from the toolbar.
2 The report loads the most recent approval = ERROR rows (adjust the Limit to pull more), then automatically checks every one against Authorize.net.
3 It opens on the Needs remedy filter — only the charged-but-uncredited deposits, with a live count. Switch to All errors to see every error row.
Tip: If "Needs remedy" is empty after the check finishes, there is nothing to fix — every errored deposit either never charged or is already credited.

The Remedy screen — the "Needs remedy" / "All errors" filter, after the Authorize.net check.

Automated daily check & email alert

The dashboard can run this check on its own. In Schedule Settings you can turn on a daily run at a set time, set how many rows to check, and enable Start at login so a missed run catches up when the machine powers on. When a run finds a deposit that was charged but never credited, an email alert is sent to the configured operator. You can also press Run now at any time.

4. Reading a row

Each row shows, top to bottom:

  • Customer & amount, then the WK reference, school, type, and date.
  • The error type (the gateway message) on an orange line.
  • Deposit status — Credited, Credited → voided, or Account not credited.
  • Authorize.net status — charged · settled, charged · pending settlement, or no charge found. A found match can be opened for full detail.
  • Verdict banner — OK or Needs remedy with the reason.
  • Action buttons: Remedy (replay deposit) and Check balance.

5. Remedying a deposit (replay)

"Remedy" re-submits the deposit's original payload so the missing transfer rows get created — it does not re-charge the card. It replays what was already paid.

1 On a Needs remedy row, click Remedy (replay deposit).
2 Confirm the dialog (it names the reference, amount, customer, and the endpoint).
3 On success you'll see "Deposit processed". Click Reload to refresh the transfer status — the row should flip to Credited.

Which endpoint runs

The dashboard picks the correct processor from the deposit type:

Deposit typeEndpoint used
Apple Pay / cardRcvApplePayTran2 (native, in-process)
ACH / eCheck (PhonFund2)FundACH2
Note: An Apple Pay deposit must never be sent to FundACH2 (that is the bank/ACH processor and will reject it). The dashboard routes by type automatically.

The double-credit guard

Safe by design: Before every replay the dashboard re-checks the transfer table live. If a transfer row already exists for that reference, it aborts and does not replay — so you cannot accidentally credit an account twice. It also aborts if the check can't be confirmed.

6. Verifying the balance

After a remedy (or any time), confirm the account reflects the credit:

1 Click Check balance on the row — it looks up the recipient's account and shows the current balance and last transfer.
2 After a successful remedy the balance should be higher by the deposit amount, and Last transfer should show the WK reference.

A standalone Balance Lookup screen is also available from the toolbar (look up by UID, barcode, or PIN).

Balance Lookup — by UID, barcode, or PIN.

Tip: Balance is read-only — it is computed from the transfer rows. The balance becomes correct when the transfers are posted; checking it just confirms the result.

7. Voiding an unsettled transaction

Use this when a charge went through but should be reversed (for example, a deposit that was credited with no valid charge, or a duplicate). Voiding only works while a transaction is still unsettled.

1 Open the Unsettled Transactions screen, search for the transaction, and open it.

Unsettled Transactions — search, then open a transaction to void it.

2 Click Void transaction and confirm.
3 On success the dashboard automatically reverses the transfer rows (posts mirror/negated rows so the reference nets to zero) and then shows the account balance after the void for each affected account.
Note: If a transaction is missing its reference (invoice) or school, the void still happens but the transfer reversal cannot run — reverse it manually and review that account.

8. SQL quick reference

The dashboard's copy buttons produce these read-only lookups. Use them to inspect a deposit by hand. Replace the bracketed values with the row's data.

The error report

SELECT * FROM fund.webtran WHERE UPPER(approval) = 'ERROR' ORDER BY counter DESC LIMIT [n];

A single webtran row

SELECT * FROM fund.webtran WHERE counter = '[counter]';

The account credit (transfer) for a deposit

SELECT * FROM `MKSdata`.transfer WHERE reference = '[WK…]' AND school = '[school]' AND qdate = '[date]';

The account holder by email

SELECT * FROM `MKSdata`.security WHERE email = '[email]';

Tip: On a timed-out row the reference column holds the error text, not the WK reference — the WK reference is "WK" + the row's counter.

9. Troubleshooting

SymptomCause & fix
Remedy says 0,NoACHAn Apple Pay deposit was sent to the ACH processor. It is now routed by type automatically; retry.
Remedy says "Unable making request … ProtocolError"The legacy web service was offline (HTTP 500). The replay now uses the native processor; retry. If it persists, the deposit service itself is down — escalate.
Remedy aborts: "transfer rows already exist"The account is already credited — the guard is protecting you. Reload to refresh the status; no action needed.
Report shows no new error typesThe broadened server query must be deployed. Until then only timeout/connection rows appear.
"No charge found" but you expect oneWiden the search window / confirm the deposit date; a charge only appears after it settles into a batch or is captured-pending.
