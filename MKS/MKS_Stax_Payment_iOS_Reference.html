1. Overview & key concepts

Stax uses a Bifrost-hosted web checkout (like Stripe): the app opens a page in a WebView, the user pays there (card / Apple Pay / Google Pay), and the page charges the card via Stax. The app is responsible for recording and crediting the deposit in the MKS ledger around that charge.

The single most important idea: there are two separate amounts / two separate systems.

ConcernWho does itNotes
Charging the cardThe hosted page + StaxAmount comes from the URL the app opens. Simple for now; hardened via a signed session (§14) before production.
Recording / crediting the depositThe app → Bifrost APIsPre-record before the page, settle after success. This is the app's job.

The deposit lands in the ledger in two stages on Bifrost:

  • Pending — created before the user pays, via RcvApplePay + UpdateApplePayResponse. Row sits in mkstemptransfer.
  • Completed — created after a confirmed charge, via RcvApplePayTran2. This is what actually inserts into the real transfer ledger and credits the student balance, and flips the temp row to Completed.
Note: This is the same two-stage model Apple Pay / Auth.Net already use. Stax differs only in that (a) the charge happens on a hosted web page instead of the native Apple Pay sheet, and (b) the deposit is tagged with gateway = "Stax".

Two ways to carry the amount & account

This guide describes the simple method first (raw params in the URL) — build and test on that. There is also a hardened signed-session method that stops a client tampering with the amount/uid; Bifrost supports both, so you switch to it at the end without a backend change. See §14 — Convert to signed sessions.

Saved cards

The page can also offer the account's previously-saved cards ("pay with a saved card"). That whole feature lives on the page + Bifrost — it keys off the same signed session, so Android gets it for free once the session flow is in place (see §12).

2. End-to-end sequence

1. User taps pay → app resolves processor = Stax
2. ↓ App calls RcvApplePay → Bifrost inserts fund.webtran, returns invoice WK…
3. ↓ App calls UpdateApplePayResponse (Raw payload tagged gateway:"Stax") → Bifrost inserts Pending mkstemptransfer
4. ↓ App opens …/Bifrost/StaxPaymentView?total=&fee=&uid=&school=&invoice=WK… in a WebView
5. ↓ User pays on the page; the page charges the card via Stax
6. ↓ On success the page navigates to mkspay://stax-success
7. ↓ App intercepts that URL, dismisses the WebView
8. ↓ App calls RcvApplePayTran2 (same Raw payload, gateway:"Stax") → Bifrost credits balances + marks temp row Completed

A hardened variant inserts a "mint signed session" step before opening the page — see §14.

3. Choosing the Stax processor

Which processor a school uses is decided by the merchant identifier that the backend returns in the Apple Pay config (applepayInfo.merchantid on iOS). iOS compares it against known identifiers:

Merchant identifierProcessor
merchant.odin.mykidsspendingAuth.Net
merchant.odin.mykidsspending.stripeStripe
merchant.odin.mykidsspending.staxStax

If the merchant id matches the Stax value, the app runs the Stax flow below. (During QA the iOS app also has a temporary override that forces Stax whenever test mode is on — that is test-only scaffolding, not part of the real contract.)

4. Step 1 — Pre-record the pending deposit

Before opening the checkout page, the app creates the pending deposit so there is a ledger record tied to a real invoice number. This is two calls.

1POST RcvApplePay — mints the invoice + inserts fund.webtran.

Request fields

FieldValue
LoginIDFrom Apple Pay config (may be empty for Stax; only used server-side for a hash)
FingerprintRandom int as string
AmountTotal (deposit + fee), 2 decimals, e.g. "1.10"
FeeFee, 2 decimals, e.g. "0.10"
TimestampUnix seconds as string
UID_PayerParent UID (fallback: first receiver UID)
UID_ReceiverReceiver UIDs only, colon-joined: uid1:uid2 (no amounts at this stage)
CC, First, LastOptional

Response: a comma-joined string hash,WK#####. Index 1 (WK#####) is the invoice number — keep it; every later call references it.

2POST UpdateApplePayResponse — inserts the Pending mkstemptransfer row.

The outer payload wraps a Raw string, which is a JSON-encoded ApplePayObject. That inner object is where gateway:"Stax" lives.

// Outer payload
{
  "InvoiceNumber": "WK#####",
  "ResponseCode":  "RcvApplePay",
  "Timestamp":     "<unix>",
  "Reference":     "RcvApplePay succeeded",
  "School":        "<school>",
  "Raw":           "<JSON string of the object below>"
}

// Raw / ApplePayObject  (built once, reused verbatim in Step 4)
{
  "InvoiceNumber": "WK#####",
  "UID_Payer":     "<payer uid>",
  "Receivers":     "uid1:amount1^uid2:amount2",   // WITH amounts here
  "Amount":        "1.00",     // DEPOSIT amount (not the total)
  "Fee":           "0.10",
  "Approval":      "0",
  "TransID":       "0",
  "gateway":       "Stax",      // <-- REQUIRED. Omit and Bifrost defaults to "Auth2"
  "qdate":         "2026-08-04",
  "time":          "13:20:05:120",
  "operator":      "ApplePay",
  "RcvdHash":      "<hmac>",
  "Timestamp":     "<unix>"
}
Tip: Build the Raw / ApplePayObject once and store it. The exact same object is what you POST to RcvApplePayTran2 in Step 4. On iOS a helper adds qdate, time, operator, RcvdHash, Timestamp to the base fields — Android needs the equivalent, because RcvApplePayTran2 rejects the payload if InvoiceNumber, qdate, or operator are missing.
Amount fields are easy to get wrong: RcvApplePay.Amount = the total (deposit+fee); the Raw.Amount = the deposit only. Receivers is UIDs-only in RcvApplePay but UID:amount pairs in the Raw.

5. Step 2 — Open the hosted checkout URL

Open the checkout page in a WebView. The URL carries the amount, fee, and account context as plain query params. (This is the simple method — the hardened signed-session upgrade is in §14; do that before production.)

Livehttps://msdata.co/Bifrost/StaxPaymentView?total=<total>&fee=<fee>&uid=<uid>&school=<school>&invoice=<WK…>
Testsame on https://test.msdata.services/…, plus &test=true

These params are client-editable. Because total/uid are plain URL params, a tampered client could change the amount or swap a uid. That's acceptable while building/testing, but is exactly what the signed-session method (§14) fixes for production. Bifrost accepts both methods, so you can build on this one now and switch later without a backend change.

6. Step 3 — Host in a WebView & intercept the return

Load the URL in a full-screen WebView. The critical part is watching every navigation for the page's return signal. When the page finishes, its JavaScript navigates the WebView to a custom-scheme URL:

mkspay://stax-success?transactionId=<stax txn id>&method=<card|apple_pay|google_pay>

iOS mechanism

iOS uses WKNavigationDelegate.decidePolicyFor navigationAction: it inspects each requested URL and, if the string contains success, treats it as done (dismiss + settle). It also recognises cancel / error as a failed/cancelled result.

Android equivalent must implement

Override WebViewClient.shouldOverrideUrlLoading. When the URL is mkspay://stax-success (or otherwise contains success): return true (do not let the WebView load the custom scheme), close the WebView, and run Step 4. Treat URLs containing cancel or error as a cancel/failure.

Note: The custom scheme mkspay:// is not a real network URL — it exists only so the page can hand control back to the native app. If Android does not intercept it, the WebView will try to load it and fail, and the deposit will never settle. This interception is the piece Android must add.
Success is checked first. Match order matters: check for success before cancel/error, and guard so the completion fires only once (the WebView can report the navigation more than once).

7. Step 4 — Settle on success

On the success signal, POST the stored Raw / ApplePayObject (the one from Step 1, including gateway:"Stax") to RcvApplePayTran2. Bifrost then inserts the real ledger rows, credits the student balance, marks the mkstemptransfer row Completed, and emails the payer.

  • Response starts with 1, on success. …,Duplicate means it was already settled — treat as success (idempotent; Bifrost dedupes).
  • On network failure, retry (iOS retries a few times).
  • On a real failure, do not mark the flow successful — leave the Pending row intact for recovery and tell the user their card was charged but the deposit could not be finalized.
Critical: RcvApplePayTran2 credits accounts regardless of whether the card actually cleared. Call it only after the page has confirmed a successful charge (i.e. only from the success signal) — never optimistically, never on cancel.

8. Cancel handling

The WebView should offer a Cancel affordance (iOS puts a "Cancel" button in the nav bar) so the user can back out. Cancel = dismiss the WebView, release any payment lock, and do not call RcvApplePayTran2. The Pending row is simply left behind. Best used before the user submits payment; if a charge is already in flight it may still complete server-side (see Gotchas).

11. Gotchas & warnings

  • gateway:"Stax" is mandatory in the Raw object for both Step 1b and Step 4. If it is missing/empty, Bifrost records the deposit under Auth2.
  • Same invoice everywhere. The WK##### from Step 1a ties webtran → temp row → settlement together. Reuse it verbatim.
  • Only settle on confirmed success (see the red note in Step 4).
  • Missed return = stuck Pending. If the app is killed after the charge but before catching mkspay://stax-success, the card is charged but the deposit stays Pending and uncredited. This is a known reliability gap in the current app-driven design.
  • Amounts are client-supplied in this simple method. The URL total (what is charged) and the Raw amounts (what is credited) are separate and unvalidated, so a tampered client could pay one amount and credit another, or swap a uid. This is why you move to the signed-session method (§14) before production — don't ship the raw-param method to real users.

12. Saved cards (bonus — free on Android)

The page can list the account's previously-saved cards and let the user pay with one instead of re-typing. This is entirely page + Bifrost; the native app does nothing extra:

  • On a successful card charge, Bifrost saves the reusable card token to fund.payment_tokens (encrypted, one per account). Cards only — wallet (Apple/Google Pay) tokens are single-use and are not stored.
  • On load, the page calls GET /staxpayment/tokens?uid= (or ?session= in the §14 method) and renders any saved cards; picking one and paying posts charge with a savedTokenCounter (never the token — the server decrypts it, keyed to the account).

Because it keys off the account (the uid you already pass in Step 2), the saved-card UI works with no additional client code. Card-on-file reuse still carries the usual stored-credential/consent requirements — flag those charges as such to Stax.

13. Google Pay note

The hosted page handles card, Apple Pay, and Google Pay through the same Stax digital-wallet path, and emits the same mkspay://stax-success redirect on success regardless of method. So no page changes are needed for Google Pay — but Android is where Google Pay actually matters, and it will only return to the app if the Android WebView intercepts mkspay://stax-success exactly as described in Step 3, then runs Step 4. In other words: implement the interception + settlement correctly and Google Pay works for free; skip it and Google Pay will charge but never credit.

14. Later — convert to signed sessions (before production)

The simple method trusts the client with total and uid in the URL — fine for building/testing, not for production. The fix is a signed session: the server hands the app a tamper-proof token carrying those values, and the page relays that token instead of raw params. Bifrost already supports both, so this is an app + page-usage change only — no backend work.

What "minting a session" means (plain version)

Instead of putting ?total=1.10&uid=… in the URL (which a proxy or tampered WebView could edit), you ask the server to build a small tamper-proof token that carries those values, and you just relay it. "Minting a session" = one HTTP call whose response is a token string you drop into the page URL. You never build the token and never hold the secret.

Analogy — a concert ticket. The box office (Bifrost) prints a ticket (the token) with your seat + price and a hologram (a cryptographic signature). You carry it to the page. At every gate (amount, tokens, charge) staff check the hologram is genuine and read the price off the ticket — you can't scribble a cheaper price on it, because the hologram wouldn't match.

What's in the token

Two base64 chunks joined by a dot: <payload>.<signature>.

PartWhat it is
payloaduid | invoice | total | fee | school | expiry. The amounts are the real ones the server read from the DB, not what the client claims.
signatureHMAC‑SHA256(payload, SERVER_SECRET) — secret is server-only, so the app can't forge or edit the token.
expiry~15 minutes; after that every endpoint rejects it.

The change (two small differences from the simple flow)

1Add a mint call right after the pre-record and before opening the page. It's a single POST:
POST https://<same bifrost host you pre-recorded on>/Bifrost/api/staxpayment/session
Content-Type: application/json

{ "uid": "<payer uid>", "invoice": "WK12345" }   // invoice = the WK… from Step 1

Bifrost finds that invoice's row in fund.webtran, reads the authoritative total/fee/school from it (this is why the client can't fake the amount — it comes from the DB, not the request), signs everything, and returns the token:

// response
{ "Success": true, "Data": "eyJ1a2Q...<the token string>...c2ln" }
//                          ^ this whole string is what you put in ?session=

On iOS this call is WebService.createStaxSession(uid:invoice:).

2Open the page with the token instead of raw params:
…/Bifrost/StaxPaymentView?session=<token>          // live
…/Bifrost/StaxPaymentView?session=<token>&test=true // test

Drop total/fee/uid/school/invoice from the URL — they're all inside the signed token now.

Nothing else changes. The page's amount/tokens/charge endpoints see the session, verify the signature + expiry, and read the values out of it. Editing the URL or the charge body now does nothing, because everything is re-derived from the signed token server-side.

Mint on the same Bifrost host/DB you pre-recorded on — the mint reads the webtran row Step 1 wrote.
Residual limitation: the mint still trusts the app-supplied uid (the MKS API is uid-trust with no per-user auth token). Someone with a valid unexpired invoice and a known uid could still mint a session. The complete fix is per-user auth on the mint — a broader MKS-API change, not Stax-specific. Don't treat the mint as an auth boundary.
