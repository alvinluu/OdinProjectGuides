1. Overview & key concepts

Stax uses a Bifrost-hosted checkout page: your web app opens that page, the user pays there (card / Apple Pay / Google Pay), and the page charges the card via Stax. Your app is responsible for recording and crediting the deposit in the MKS ledger around that charge.

Two separate concerns:

ConcernWho does it
Charging the cardThe hosted page + Stax. The amount comes from the URL (or, hardened, a signed session — §12).
Recording / crediting the depositYour app → Bifrost APIs: pre-record before the page, settle after success.

The deposit lands in the ledger in two stages on Bifrost:

  • Pending — created before the user pays, via RcvApplePay + UpdateApplePayResponse. Row sits in mkstemptransfer.
  • Completed — created after a confirmed charge, via RcvApplePayTran2. This inserts into the real transfer ledger, credits the balance, and flips the temp row to Completed.
No sandbox. Stax has no test/sandbox mode — every Stax charge is a real, live charge, on any deployment. Never present a "no real charge" message; test with a real card and a small amount.
Call the Bifrost APIs from your server, not the browser, where you can. RcvApplePayTran2 credits accounts based on its payload, so it should not be freely callable from a page a user controls. A web app should proxy the pre-record and settlement through its own backend, and/or use the signed-session hardening (§12). (Native apps call them directly; a browser is a more hostile client.)

2. End-to-end sequence

1. User clicks pay → app resolves processor = Stax
2. ↓ App (server) calls RcvApplePay → Bifrost inserts fund.webtran, returns invoice WK…
3. ↓ App (server) calls UpdateApplePayResponse (Raw payload tagged gateway:"Stax") → Bifrost inserts Pending mkstemptransfer
4. ↓ App opens …/Bifrost/StaxPaymentView?total=&fee=&uid=&school=&invoice=WK… in an iframe or popup
5. ↓ User pays on the page; the page charges the card via Stax
6. ↓ On success the page postMessages the result to your app
7. ↓ App closes the iframe/popup
8. ↓ App (server) calls RcvApplePayTran2 (same Raw payload, gateway:"Stax") → Bifrost credits balances + marks temp row Completed

A hardened variant replaces the raw URL params with a signed session token — see §12.

3. Choosing the Stax processor

Which processor a school uses is decided by the merchant identifier the backend returns in the payment config. If it's the Stax value, run the Stax flow below. (Other values route to Auth.Net / Stripe — out of scope here.)

4. Step 1 — Pre-record the pending deposit

Before opening the page, create the pending deposit so there's a ledger record tied to a real invoice. Two calls (do these from your backend).

1POST RcvApplePay — mints the invoice + inserts fund.webtran.
FieldValue
LoginIDFrom payment config (may be empty for Stax; only used server-side for a hash)
FingerprintRandom int as string
AmountTotal (deposit + fee), 2 decimals, e.g. "1.10"
FeeFee, 2 decimals
TimestampUnix seconds as string
UID_PayerPayer uid (the parent/account paying)
UID_ReceiverReceiver uids only, colon-joined: uid1:uid2 (no amounts here)

Response: hash,WK#####. Index 1 (WK#####) is the invoice — keep it; every later call references it.

2POST UpdateApplePayResponse — inserts the Pending mkstemptransfer row.

The outer payload wraps a Raw string, a JSON-encoded ApplePayObject. That inner object carries gateway:"Stax".

// Outer payload
{ "InvoiceNumber":"WK#####", "ResponseCode":"RcvApplePay", "Timestamp":"",
  "Reference":"RcvApplePay succeeded", "School":"", "Raw":"" }

// Raw / ApplePayObject (build once; reused verbatim in Step 4)
{ "InvoiceNumber":"WK#####", "UID_Payer":"",
  "Receivers":"uid1:amount1^uid2:amount2",   // WITH amounts here
  "Amount":"1.00",   // DEPOSIT amount (not the total)
  "Fee":"0.10", "Approval":"0", "TransID":"0",
  "gateway":"Stax",  // <-- REQUIRED. Omit and Bifrost defaults to "Auth2"
  "qdate":"2026-08-06", "time":"13:20:05:120", "operator":"ApplePay",
  "Timestamp":"" }
Tip: Build the Raw / ApplePayObject once and store it — the same object is what you POST to RcvApplePayTran2 in Step 4. RcvApplePayTran2 rejects the payload if InvoiceNumber, qdate, or operator are missing.
Amount fields differ per call: RcvApplePay.Amount = the total; the Raw.Amount = the deposit only. Receivers is UIDs-only in RcvApplePay but UID:amount pairs in the Raw.

5. Step 2 — Open the hosted checkout page

Open the checkout page in an iframe (in-page modal) or a popup window. The URL carries the amount, fee, and account context as query params:

EnvURL
Prodhttps://msdata.co/Bifrost/StaxPaymentView?total=<total>&fee=<fee>&uid=<uid>&school=<school>&invoice=<WK…>
Stagingsame on https://test.msdata.services/… (still a real charge — no sandbox)
HTTPS only. Card entry, Apple/Google Pay, and being embeddable all require the page to be served over HTTPS. Use the HTTPS hosts above (never a bare-IP/HTTP host).
These params are client-editable (a user can change total/uid). Fine for early integration; the signed-session method (§12) fixes it for production.

6. Step 3 — Detect completion (postMessage)

This is the one real difference from the native guide. Native apps intercept a custom-scheme redirect (mkspay://stax-success) in a WebView. A browser can't do that (and can't observe a cross-origin iframe's navigation), so the page signals the result to your app with window.postMessage, and your app listens for it.

Page prerequisite: the hosted page currently emits the native mkspay://stax-success redirect. For web embedding it must also postMessage the result to its opener/parent. That's a small addition to PaymentForm.cshtml (call it alongside the existing native signal). Coordinate with the Bifrost team.

Page side (what the hosted page sends on success)

window.parent.postMessage(
  { source: 'stax-checkout', result: 'success', transactionId: txId, method: method },
  '*'  // or the specific web-app origin
);
// on cancel/error: { source:'stax-checkout', result:'cancel' | 'error', ... }

Web app side (listen, then settle)

window.addEventListener('message', function (e) {
  // ALWAYS validate the origin/shape before trusting it.
  if (e.origin !== 'https://msdata.co' && e.origin !== 'https://test.msdata.services') return;
  var d = e.data || {};
  if (d.source !== 'stax-checkout') return;

  closeCheckout();                 // remove the iframe / close the popup
  if (d.result === 'success') {
      settleDeposit(invoice, d.transactionId);   // Step 4 (via your backend)
  } else {
      releaseAndReset();           // cancel/error -> do NOT settle
  }
});
Guard against double-firing (a page can post more than once) and always verify e.origin — never act on a message from an unexpected origin.

7. Step 4 — Settle on success

On the success message, POST the stored Raw / ApplePayObject (from Step 1, including gateway:"Stax") to RcvApplePayTran2 — ideally from your backend. Bifrost inserts the ledger rows, credits the balance, marks the temp row Completed, and emails the payer.

  • Response starts with 1, on success. …,Duplicate means already settled — treat as success (idempotent).
  • On network failure, retry.
  • On a real failure, do not mark success — leave the Pending row for recovery and tell the user their card was charged but the deposit couldn't be finalized.
Critical: RcvApplePayTran2 credits accounts regardless of whether the card actually cleared. Call it only after the page's success message — never optimistically, never on cancel.

8. Cancel handling

Offer a Cancel/close affordance on the modal. Cancel = close the iframe/popup and do not call RcvApplePayTran2; the Pending row is simply left behind. Best used before the user submits payment; a charge already in flight may still complete server-side.

9. Endpoint & payload reference

Base paths: API calls go to the Bifrost API base (…/Bifrost/api/…); the hosted page is at …/Bifrost/StaxPaymentView (not under /api/). Prod host msdata.co, staging test.msdata.services — always HTTPS.

There are two response conventions — know which you're parsing:

  • The three Apple Pay endpoints return a plain comma-delimited string (not JSON): first field is a status (1 = ok, 0 = fail; or a hash for RcvApplePay).
  • All /api/staxpayment/* endpoints return JSON wrapped in MobilePaymentResponse<T>: { "Success": bool, "Message": string, "Data": T }.
Legend — must-use vs. swap-for-your-own:
  • Stax-required — the actual card charge. This is the Stax payment. Use Bifrost's (or do your own Stax.js tokenization against the same Stax merchant). Without it, no money moves.
  • MKS ledger · replaceable — MKS bookkeeping that records/credits the deposit in the MKS ledger. Not Stax. If your web app is a different product with its own accounts/deposit system, replace these with your own endpoints. If this is the MKS web app you do need them (they're what credits the student's account) — but they're still not part of the Stax charge.
  • optional — enhancements you can skip entirely: signed-session hardening, saved cards, method validation, client-error logging.
The one thing to internalize: the Stax charge (hosted page / charge) and the MKS deposit recording (RcvApplePay → UpdateApplePayResponse → RcvApplePayTran2) are independent. The charge moves money at Stax; the trio records that deposit in MKS. A non-MKS web app keeps the charge and replaces the trio with its own.

9.1 Endpoints your app calls

Around the hosted page, your app (ideally its backend) calls these four. The rest (§9.2) are called by the page. Note that the first three are the MKS ledger · replaceable trio — none of them touch Stax.

① POST /api/RcvApplePay — mint invoice + insert fund.webtran Step 1a MKS ledger · replaceable

Validates the request, computes an HMAC hash over LoginID^FingerPrint^Timestamp^Amount, inserts a pending fund.webtran row (payer's security group + receiver), and returns the hash plus a freshly generated WK invoice number.

Request body — RcvApplePayRequest (all fields string). Required: Amount, FingerPrint, Timestamp, UID_Payer, UID_Receiver (missing any → 400 "Missing amount, fingerprint, timestamp, uid_payer, or uid_receiver").

{
  "LoginID":     "",              // config; may be empty for Stax
  "FingerPrint": "839201",        // required — random int as string
  "Amount":      "1.10",          // required — TOTAL (deposit + fee), 2 dp
  "Fee":         "0.10",
  "Timestamp":   "1754870400",    // required — unix seconds as string
  "UID_Payer":   "",   // required
  "UID_Receiver":"uid1:uid2",     // required — receiver UIDs only, colon-joined (no amounts)
  "School":      "",
  "CC":"", "First":"", "Last":"", "Approval":"", "Reference":"",
  "TransactionID":"", "RefID":"", "ResponseCode":"", "InvoiceNumber":"", "Raw":""
}

Response (plain string): "<hash>,WK#####" on success (index 1 = the invoice). DB failure → "0,<log>".

② POST /api/UpdateApplePayResponse — insert Pending temp row Step 1b MKS ledger · replaceable

Deserializes the Raw JSON into an ApplePayObject, overrides its qdate/time from the matching fund.webtran row, inserts the deposit into mkstemptransfer as Pending, and stamps the webtran row with the full response.

Request body — same RcvApplePayRequest model; the fields that matter here are InvoiceNumber, School, Reference, and Raw (a JSON-encoded ApplePayObject, see ③ for its shape). Set ResponseCode:"RcvApplePay", Reference:"RcvApplePay succeeded".

{
  "InvoiceNumber":"WK12345",
  "ResponseCode": "RcvApplePay",
  "Timestamp":    "1754870400",
  "Reference":    "RcvApplePay succeeded",
  "School":       "",
  "Raw":          "{ ...JSON of the ApplePayObject, incl. \"gateway\":\"Stax\"... }"
}

Response (plain string): "1,Updated" on success, "0,<log>" on failure. (Always HTTP 200.)

③ POST /api/RcvApplePayTran2 — settle: credit + mark Completed Step 4 MKS ledger · replaceable

Validates the payload, then inserts the real transfer ledger rows and credits the balances (marking the temp row Completed). This is the money-moving call — run only after a confirmed charge.

Request body — the ApplePayObject itself (this is the same object you JSON-encoded into Raw in ②). Watch the casing — several keys are lowercase. Required: InvoiceNumber, qdate, operator.

{
  "InvoiceNumber":"WK12345",
  "UID_Payer":    "",
  "Receivers":    "uid1:amount1^uid2:amount2",  // WITH amounts, caret-joined
  "Amount":       "1.00",        // DEPOSIT only (not the total)
  "Fee":          "0.10",
  "gateway":      "Stax",        // lowercase key — REQUIRED, else recorded as "Auth2"
  "school":       "",    // lowercase
  "qdate":        "2026-08-10",  // lowercase — REQUIRED
  "time":         "13:20:05:120",// lowercase
  "operator":     "ApplePay",    // REQUIRED (C# field is @operator)
  "Approval":"0", "TransID":"0", "Timestamp":"1754870400"
}

Response (plain string, HTTP 202): "1,success". Failure → "0,failure,<msg>". If already settled you'll see a duplicate/failure marker — treat an already-completed invoice as success (idempotent).

Missing-field errors come back as "0,Invoice number is required." / "0,Date is required." / "0,Operator is required." — usually a casing or field-name mismatch on qdate/operator.

④ POST /api/staxpayment/session — mint a signed session optional · §12

Reads the authoritative total/fee/school from fund.webtran for the invoice and returns a 15-minute signed token binding uid+invoice+amount. Used to replace the raw URL params (see §12).

Request body — SessionRequest: Uid (string, required), Invoice (string, required).

// request                       // response (MobilePaymentResponse<string>)
{ "Uid":"",                  { "Success": true, "Message": null,
  "Invoice":"WK12345" }             "Data": "" }

Errors: 400 "uid and invoice are required." or "Unknown invoice."

9.2 Endpoints the hosted page calls

Two ways to use these:

  • Reuse Bifrost's hosted page (the flow in this guide) — you call none of these; the StaxPaymentView page calls them for you using the ?session=/?uid=/?total= it was opened with.
  • Build your own checkout (own Stax.js tokenization) — then only charge is Stax-required; everything else here you compute/skip yourself.

All return MobilePaymentResponse<T>.

GET /api/staxpayment/amount — display amount for the page optional · hosted-page only

Query: ?session=<token> (preferred) or ?total=<decimal> (legacy).
Data = PaymentAmountResponse: AmountDisplay (string), Amount (decimal), Fee (decimal), ButtonLabel (string, e.g. "Pay $25.00"). Prefers the signed session; raw total is testing-only.

GET /api/staxpayment/tokens — list saved cards (see §11) optional

Query: ?session=<token> (preferred) or ?uid=<uid> (legacy).
Data = List<PaymentTokenSummary>: Counter (int), DisplayLabel (string, e.g. "Visa ••4242"), TokenType (short), LastUsed (string). Never returns the raw token; uid is taken from the session so a raw uid can't enumerate another account.

POST /api/staxpayment/charge — charge the card via Stax Stax-required

The page tokenizes the card with Stax.js, then posts this to charge it. Request — ChargeRequest: PaymentMethodId (string), Total (decimal), PaymentMethod ("card"/"apple_pay"/"google_pay"), Session (signed token), Uid, School, Invoice, NameOnAccount, SavedTokenCounter (int; >0 = charge a saved card), SaveCard (bool), CustomerId, Memo. A valid Session overrides uid/invoice/school/total with server-authoritative values.
Data = ChargeResult: Success, TransactionId, Message, LastFour, CardType, Total, PaymentMethod, RawResponse (on failure). Charge decline → HTTP 402.

POST /api/staxpayment/validate & POST /api/staxpayment/logclienterror optional

validate — body { "PaymentMethodId":"…", "CustomerId":"…" }, Data = bool (does the tokenized method exist/usable, without charging). logclienterror — body { "Stage":"…", "Message":"…", "Detail":"…" }, logs a Stax.js error server-side (this is how the page routes its diagnostics to portable logs).

10. Gotchas & warnings

  • No sandbox — charges are real. Every Stax charge is live on any host.
  • gateway:"Stax" is mandatory in the Raw object for Step 1b and Step 4, or Bifrost records the deposit under Auth2.
  • Same invoice everywhere. The WK##### ties webtran → temp row → settlement together. Reuse it verbatim.
  • Settle only on the success message (see §7).
  • Missed message = stuck Pending. If the user closes the tab after the charge but before you handle the success postMessage, the card is charged but the deposit stays Pending. Consider a server-side reconciliation for orphaned Pending rows.
  • Validate postMessage origin and never trust amounts/uids the browser could tamper with — prefer server-side calls and the signed session (§12).

11. Saved cards (bonus)

The page can list the account's previously-saved cards and let the user pay with one. It's entirely page + Bifrost:

  • On a successful card charge where the user ticked "Save this card", Bifrost stores the reusable card token in fund.payment_tokens (encrypted, one per account). Cards only — wallet (Apple/Google Pay) tokens aren't stored.
  • On load, the page calls GET /api/staxpayment/tokens?uid= (or ?session= with §12) and renders saved cards; picking one and paying posts a savedTokenCounter — the server decrypts the token, keyed to the account. The browser never sees the token.

Card-on-file reuse carries the usual stored-credential/consent requirements — flag those charges as such to Stax.

12. Signed sessions (recommended for production)

The raw-param method above trusts the browser with total and uid in the URL — a tampered client could change the amount or swap a uid. The fix is a signed session: the server hands you a tamper-proof token that carries those values, and the page relays it instead of raw params. Bifrost already supports both, so this is a page-usage change, not backend work.

What "minting a session" means

Instead of ?total=1.10&uid=… (editable by anyone who can see the URL), you ask the server to build a small tamper-proof token carrying those values, and you just relay it. Minting = one HTTP call whose response is a token string you drop into the page URL. You never build the token and never hold the secret.

Analogy — a concert ticket. The box office (Bifrost) prints a ticket (the token) with your seat + price and a hologram (a cryptographic signature). At every gate (the amount, tokens, and charge endpoints) staff check the hologram is genuine and read the price off the ticket — you can't scribble a cheaper price on it.

What's in the token

Two base64 chunks joined by a dot: <payload>.<signature>.

PartWhat it is
payloaduid | invoice | total | fee | school | expiry. Amounts are the real ones the server read from the DB — not what the client claims.
signatureHMAC‑SHA256(payload, SERVER_SECRET) — secret is server-only, so the client can't forge or edit the token.
expiry~15 minutes; after that every endpoint rejects it.

The change (two small differences)

1Mint: POST /api/staxpayment/session with body { "Uid":"<payer uid>", "Invoice":"WK#####" } (the invoice from Step 1; see §9.1 ④). Bifrost reads the authoritative total/fee/school from fund.webtran, signs it, and returns the token in Data:
// response
{ "Success": true, "Data": "eyJ1a2Q...<the token string>...c2ln" }
//                          ^ this whole string is what you put in ?session=
2Open the page with the token instead of raw params:
https://msdata.co/Bifrost/StaxPaymentView?session=<token>              // prod
https://test.msdata.services/Bifrost/StaxPaymentView?session=<token>   // staging

Drop total/fee/uid/school/invoice — they're all inside the signed token. The page's amount/tokens/charge endpoints verify the signature + expiry and read the values from it. Editing the URL now does nothing. (No test param — Stax has no sandbox.)

Mint on the same host you pre-recorded on (the mint reads that host's webtran and signs with that host's secret; the page must verify with the same secret).
Residual: the mint still trusts the app-supplied uid (the MKS API is uid-trust). Do this from your backend and don't treat the mint as an auth boundary.
