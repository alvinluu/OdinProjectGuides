1. Overview

RcvTran2Controller is the modern endpoint for submitting order transactions from the Odin Mobile POS app. It accepts a structured JSON body with a typed items array, replacing the legacy comma-separated string encoding used by RcvTranController.

This endpoint handles orders only. Credit card and account transactions continue to use POST /api/mobile/RcvTran.

Backward compatibility: RcvTranController still works and internally converts its comma-separated format into the same RcvTran2Request structure before processing. Both endpoints share a single implementation in ParseOrderService.ParseOrderJson.

3. Request Body

Top-Level Fields

4. Processing Flow

1 Save raw request. The full JSON body is inserted into the raw transaction log before any processing begins.

2 Resolve date. If qdate is absent but orderDate (Unix timestamp) is present, qdate is derived automatically.

3 Look up student. Fetched by uid. If uid is "0" (cash/credit order), looked up by id_number + school instead. Returns an error if not found or if the student's school does not match.

4 Duplicate check. The combination of school, student ID, today's date, and orderID is checked. Duplicate orders are rejected.

5 Resolve paycode. Uses paycode from the request. If omitted, derives it from the student's account type. All resolved paycodes are validated — an unrecognised code returns an error.

6 Resolve location & area. Validates the area exists in portable.area. If pulocation is set, its description is appended to the receipt text.

7 Resolve departments. For each item that omits department, fetches the department code from portable.stock by PLU. Missing PLUs default to "0".

8 Write orders. Each line item is written to portable.order. If location > 10, it is also written to mksdata.lunchorder.

9 Send receipt. An HTML receipt email is sent if an address is available from the request or the location configuration.

5. Response Format

All responses return a MobileResponse JSON object with HTTP 202 Accepted.

Success

{
  "status":    1,
  "message":   "",
  "log":       "",
  "data":      "",
  "overwrite": true
}

Failure

{
  "status":    0,
  "message":   "<error detail>",
  "log":       "",
  "data":      "",
  "overwrite": true
}
FieldTypeDescription
statusint1 on success, 0 on any failure.
messagestringEmpty on success. Error description or full server log on failure.
logstringAdditional server-side log output. May be empty.
dataobjectEmpty string for this endpoint — no payload is returned on order submission.
overwriteboolAlways true.
Always check status, not the HTTP status code. All responses — including validation errors and null-body requests — return HTTP 202 Accepted. A status of 0 means the order was not saved.

7. Notes & Edge Cases

Location normalization

If location is a number greater than 20, only its first character is used. For example, "31" becomes "3". This normalization happens in the controller before ParseOrderJson is called.

Cash / credit orders (uid = "0")

Set uid to "0" for orders where the patron pays by cash or credit card. The handler then looks up the student by id_number + school. If you do not need to associate the order with a specific student, leave id_number empty — the order is saved with ID 0.

Duplicate order prevention

Orders are deduplicated using the combination of school, student id_number, today's date, and orderID. Retrying with the same orderID on the same date is rejected. Always generate a unique orderID per order on the client.

Per-item paycode

The paycode field accepts a single code or a comma-separated list. When a list is provided, each item receives the code at its matching index. If the list is shorter than the item count, the first code is used for all remaining items.

lunchorder vs order table

  • location ≤ 10 — written to portable.order only.
  • location > 10 — written to both portable.order and mksdata.lunchorder.

Error emails

In production, when ParseOrderJson returns an error the server automatically sends a parse-error alert with the full request JSON and error log attached. This does not happen in debug builds.
