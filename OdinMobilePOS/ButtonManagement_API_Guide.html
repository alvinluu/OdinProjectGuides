1. The big picture

A “button” on the POS sales screen is one item tile. Buttons are grouped onto tabs (pages/categories), and some buttons open a submenu (modifiers / choices). The iPad is the editor and the renderer; Bifrost + MySQL is the system of record. Three MySQL tables hold the layout — buttons, tabs, submenu — and the iPad mirrors them into three Core Data entities.

Naming trap — read this first. The app does not have a Button entity. On the iPad:
  • a button is a Favorite row,
  • a tab is a Department row,
  • a submenu entry is a SubMenu row.
On the server the tables are named for what they are (buttons, tabs, submenu). Keep this mapping in your head for the rest of the doc.

Two more things to internalize up front:

  • One endpoint does both directions. There is no separate GET. The iPad POSTs to Buttons with a list of changed buttons to push; if it sends an empty list, Bifrost treats the call as a pull and returns the current rows. Same for Tabs and SubMenu.
  • Identity rides on every request. Setting.profileParam attaches school, serial, uid, and (for POS) area to every sync call. That tuple is how the server decides which rows are “this device’s.”

And the thing this doc now makes explicit: there are two layout designs, and which one is active is a per-device setting. Sections 6 and 7 treat each one on its own.

2. Two layout designs at a glance

The app can render buttons in one of two fundamentally different layouts, chosen by Setting.buttonStyleMode (changed in Settings → Setting2VC). The mode is an Int defined in Theme/ButtonStyle.swift:

  • ButtonStyle.GRID = 0 and ButtonStyle.LIST = 1 → the iPad layout (Design A).
  • ButtonStyle.CLOUD = 2 → the Cloud Workstation layout (Design B).

Helpers ButtonStyle.isGridView(_) / isListView(_) / isCloudView(_) branch on it throughout the code. The mode decides which system value the app requests, which server rows come back, and how buttons attach to tabs:

The same three tables (buttons/tabs/submenu) store both; the system/type value (2 vs 8) is what separates them.

What lives only on one side

The iPad entity and the MySQL table are not column-for-column identical. Knowing the gaps saves hours:

  • Server-only (not on Favorite): school, serial, height, width, glyph, layoutId. On the iPad, school/serial are device-level (in Setting, sent via profileParam); height/width are layout constants computed by the collection view; glyph/layoutId are managed by the web Button Manager, not the iPad.
  • iPad never writes geometry size. Even though the iPad sends top/left (grid position), the backend’s device-save path deliberately omits top/left/height/width/glyph (ButtonsRepository.UpdateButton). Geometry is treated as iPad-managed; the web admin owns the full grid.

4. The API endpoints

All button calls are POST, JSON body, built with Alamofire inside WebService and hit Setting.bifrostPath (release: https://msdata.co/bifrost/api/). Endpoint strings come from the WSEndpoint enum (WebService.swift ~line 28). On the server they route as api/mobile/<Name> (WebAPI 2, routed by controller name).

Request envelope. Every push looks like { ...profileParam, "transactions": [ {row}, {row} ], "system": "<SystemCode>" } (tabs use the key "type" instead of "system"). The response is either a bare array of rows, or { "data": [...], "overwrite": bool, "message": "..." }, or an error { "ExceptionMessage": "..." }. The overwrite flag tells the iPad “this is the full set, prune anything missing.”

5.5  ipadconfig, prtblconfig, portableLayout (adjacent tables)

  • ipadconfig — per-device settings + telemetry. Columns include serial, school, setting (a JSON blob of device settings), sync (pending-setting flag), force_export_db, pend_tran, uid, appname, appversion, uploaded_count, push tokens. The OdinAuth heartbeat upserts this row and reads back setting + the sync/force_export_db flags.
  • prtblconfig — per-device item configuration for the scanner / manual entry (plu, barcode, amount, qty, taxable, allow-flags). This is not the button grid; don’t confuse it with buttons.
  • portableLayout — a named grouping of buttons+tabs for a school+location. buttons.layoutId / tabs.layoutId reference portableLayout.id. Managed by the web Button Manager, not the iPad.

6. Design A — iPad layout (per-device grid)

buttonStyleMode = GRID (0) or LIST (1)   system / type = 2

This is the classic layout: each iPad builds and owns its own button grid. Buttons are stored per device, keyed by the device serial. Editing a button here changes only this device — unless you explicitly push it to another device from the editor.

How buttons attach to tabs

A button’s home tab is its tab number, and its position inside the tab is the grid coordinate top/left (converted to a linear cell index by WebBMConversion().toIndexNextRow(columnCount:top:left:tabKey:)). Tabs (Department) are matched to their server row by dept_code + area.

What comes back from the server

When buttonStyleMode is grid/list, the download sends system = SystemCode.IPAD (2) (SettingTab1.fetchButtonsConfig, line 1764; tabs send type = 2 in fetchTabsConfig, line 1571). The server returns only this device’s own rows:

SELECT * FROM buttons
WHERE school = @school
  AND location IN (<area list>)
  AND plu <> ''
  AND (system IS NULL OR system <> '8')   -- exclude cloud rows
  AND serial = @serial;                    -- THIS device only

Import & upsert rules (iPad mode)

  • Buttons are upserted by (plu, area, tab) — Favorite.loadFavorite. A row with a new (plu, area, tab) is inserted; an existing one is updated in place.
  • Tabs import keeps only rows with type ≠ 8; a row whose type == 8 is rejected in iPad mode (Tab.updateTab, lines 77-81). Existing tabs matched by dept_code + area.
  • Save match (server): ButtonsRepository.ButtonExists matches by serial + location + plu + tab + school when the incoming counter == 0.
In one line: iPad layout = serial-scoped rows, tab-by-number, grid geometry, upsert on (plu, area, tab). It’s the layout the on-device button editor writes to.

7. Design B — Cloud Workstation layout (shared)

buttonStyleMode = CLOUD (2)   system / type = 8

This is the shared layout: one button set authored on the Cloud Workstation (and the web Button Manager), pushed down to every device in the school identically. The rows are not tied to any one device’s serial — they carry system = '8' and are returned to any serial that asks.

How buttons attach to tabs

Here the link is not the tab number — it is tabid. A button belongs to a tab when Favorite.tabid == Department.serial (see Favorite.isOnTab). So the tab’s serial field acts as the tab’s identity, and each cloud button stores that identity in tabid.

What comes back from the server

When buttonStyleMode == CLOUD, the download sends system = SystemCode.CLOUDWORKSTATION (8) (fetchButtonsConfig, lines 1765-1767; tabs send type = 8, fetchTabsConfig lines 1572-1573). The server returns the shared set, ignoring serial:

SELECT * FROM buttons
WHERE school = @school
  AND location IN (<area list>)
  AND plu <> ''
  AND system = '8';          -- shared across EVERY serial (no serial filter)

On the way out, PrbButton.convertTypeFromCW() remaps the button type for system == '8' rows so the iPad’s type enum lines up with the cloud authoring tool’s values.

Import & upsert rules (cloud mode)

  • Buttons are upserted by tabid — Favorite.loadFavoriteTabID (preferred whenever tabid is present).
  • Tabs import keeps only rows with type == 8; non-8 rows are rejected in cloud mode (Tab.updateTab, lines 73-76). Existing tabs matched by tab + area.
  • Sharing: because there is no serial predicate, a change authored centrally reaches every device on its next re-sync.
Why a button “appears on one iPad but not another.” It usually comes down to which design authored it. A per-device (system = 2) button only exists under its own serial, so other devices never see it. A cloud (system = 8) button is shared. If a device is in the “wrong” buttonStyleMode, it requests the other system value and the rows it’s looking for simply aren’t in the response.
In one line: Cloud Workstation layout = school-wide shared rows (system = 8), tab-by-tabid, upsert on tabid, authored centrally and mirrored to every device.

8. The sync flow, end to end

The mechanics below are shared by both designs; the only difference is the system/type value the app requests (Section 2) and the match keys (Sections 6–7).

Download (server → iPad)

The canonical download is the full button re-sync, SettingTab1.fetchButtonsConfig():

1 POST bifrostPath + "Buttons" with an empty transactions list and system = IPAD or CLOUDWORKSTATION depending on buttonStyleMode.
2 On success, delete all FAVORITE rows, then re-import the returned rows via Favorite.addButtonsToCoreData(..., isResync: true).
3 Stamp LastUpdateObj.updateLastUpdateDate(.FAVORITE, ...) and chain to the next step (patron photos, etc.).

Merge rules inside addButtonsToCoreData → updateButton → insertFavoriteJSON: rows with empty plu are skipped; upsert is by tabid when present (cloud), otherwise by (plu, area, tab) (iPad); removeButtonsMissingFrom prunes server-origin rows (counter > 0) that are absent from a full download, scoped to the areas the response actually covered; removeOrphanButtons drops buttons whose PLU is no longer in Inventory.

Edit & pending-key tracking

The button editor is ButtonConfigVC (also FavoriteVC; manager-side ButtonManagerVC). Local edits go through Favorite static mutators — updateFavorite, updateHidden, updateColor — and each one:

  1. calls markPendingUpload(plu, area:) first, which adds the key "plu|area" to Favorite.pendingUploadKeys (persisted in UserDefaults "FavoritePendingUploadKeys"),
  2. updates every matching tab-row in Core Data,
  3. saves via CoreDataService().save.

So edits accumulate a set of “dirty” buttons that haven’t been pushed yet.

Upload (iPad → server)

On save/exit, ButtonConfigVC.confirmExit() runs: uploadButtons(false, nil) → then uploadTabs(false, nil) → CoreDataService().save → a GetAuthenticate probe (to decide whether to offer “save to another device”). uploadButtons builds transactions from Favorite.toDictionary() (group_plu, plu, favorite, hidden, tab, caption, color, type, location, counter=0), wraps it with profileParam, adds system = SystemCode.IPAD, and merges the server’s response back in.

Delta sync & the empty-list trick

Two layers of “only move what changed”:

  • App side: uploadButtons sends only the buttons whose key is in pendingUploadKeys. On success those keys move to recentlyUploadedKeys and clear from pending.
  • Server side: the request carries row_count + timestamp. If the device’s row_count matches the server’s distinct count and the timestamp is valid, the server returns only rows with timestamp > @timestamp (a delta). Otherwise it resends everything and flags overwrite = true.
The empty-list guard is load-bearing. If nothing is pending, the iPad sends an empty transactions array, which Bifrost answers as a read. This is deliberate: it stops a device with no local edits from pushing a stale/empty layout and wiping the server copy. If you ever “optimize” the upload path, keep this behavior.

What triggers a sync

  • Explicit save — leaving the button editor (confirmExit) pushes buttons + tabs.
  • Manual Re-Sync — SettingTab1.reSync(...) runs the full fetch chain including fetchButtonsConfig (wipe-and-reimport of FAVORITE).
  • Server-pushed re-sync — DeviceFlagPoller polls the OdinAuth heartbeat on a Remote-Config interval. When the server returns sync == true, the app runs a silent full re-sync (reSync(silent:)), and the server clears the flag. This is how a Cloud Workstation / web Button Manager change reaches live iPads.

9. Gotchas & caveats

  • Buttons/Tabs incremental autosync is intentionally OFF. AutoSyncWebservice.autoSyncOperations early-returns for .Buttons/.Tabs (comment: “Disable because buttons goes blank”). The chunked-merge code still exists but is unreachable for those two. The only live button paths are the explicit editor save and the full Re-Sync. SubMenu and Department still sync through the operation queue.
  • Mode mismatch hides buttons. A device in GRID/LIST asks for system = 2; a device in CLOUD asks for system = 8. Point a device at the wrong mode and its buttons “disappear” even though the rows exist — it’s requesting the other design’s set.
  • Button entity is Favorite, not Button. Grepping for “Button” will send you to UI, not the model.
  • counter is forced to 0 on push. The iPad never trusts its local counter when uploading; the server matches by natural key and owns the real id.
  • Geometry asymmetry. iPad sends top/left but the backend device-save ignores top/left/height/width/glyph. Don’t expect an iPad move to repaint the web-admin grid.
  • SubMenu delete is soft (enabled = 0); tabs delete is hard (DELETE). Different lifecycles across the three tables.
  • Backend sharp edges (backend team): TabsRepository.GetTabs interpolates school straight into the SQL string (not parameterized); PrtblConfigRepository reads the taxable column into dept_code (looks like a bug). Flagging for awareness, not for this doc’s scope.
Fast path for a bug report. “A button won’t show up” → check (1) is plu empty? (2) what buttonStyleMode is the device in, and does the row’s system (2 vs 8) match? (3) for iPad mode, does serial/school/location match; for cloud mode, is system = 8 and tabid set to a real tab’s serial? (4) was it pruned by removeOrphanButtons because its PLU left Inventory? “An edit won’t save” → check pendingUploadKeys got the "plu|area" key and that confirmExit actually ran uploadButtons.
