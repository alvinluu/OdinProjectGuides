1. Overview

Apple Pay on the Web requires proving ownership of every domain that will display an Apple Pay button. Apple (or the payment processor acting on Apple's behalf) does this by fetching a specific verification file from a fixed, well-known path on the domain. This guide covers the general process, then documents the gateway-specific issues encountered while verifying domains through Stax.

2. General Verification Process

1 Get the verification file — either from the Apple Developer portal (Certificates, Identifiers & Profiles → Merchant ID → Apple Pay on the Web → add domain), or from the payment processor's dashboard (e.g. Stax, Stripe, Braintree), which generates or hosts the same file.
2 Host the file at the required path, served over HTTPS with no redirects and no authentication:
https://yourdomain.com/.well-known/apple-developer-merchantid-domain-association
3 Register the domain in the Apple Developer portal or processor dashboard and trigger verification — it fetches the file and confirms the contents match.
4 Re-verify periodically. If the file becomes unreachable, Apple Pay stops working on that domain until it's fixed.

Common Gotchas

  • The file is extensionless — no .txt or other extension, and the exact filename must match.
  • Domain matching is exact: www.example.com is not the same domain as example.com.
  • CDNs/proxies (Cloudflare, etc.) can strip the file, force an unexpected Content-Type, or block it behind auth/geo rules.
  • Only registered domains you control work — no localhost or bare IPs.

3. Stax (msdata.co / test.msdata.services)

Domains verified: test.msdata.services (staging) and msdata.co (production), both routed through the Stax gateway.

Source: docs.staxpayments.com/docs/using-apple-or-google-pay

3.1 Official Stax Setup Steps

Per Stax's own documentation (Using Apple or Google Pay), Apple Pay requires a digital signature file to be accessible on the payment site:

1 Download the signature file from https://app.staxpayments.com/.well-known/apple-developer-merchantid-domain-association.
2 Place the file at https://[merchantOrPartnerDomain]/.well-known/apple-developer-merchantid-domain-association on each payment domain, where [merchantOrPartnerDomain] is the URL of the payment site.
Note: Browsers often append .txt to the download automatically. Before uploading, rename the file so it's served as either apple-developer-merchantid-domain-association.txt or fully extensionless (apple-developer-merchantid-domain-association, no extension at all) — whichever the hosting server is configured to serve correctly. See the IIS MIME mapping issue below if the extensionless version 404s.
3 Copy the same file to every domain that displays a payment flow using Stax.js or a white-labelled version of Stax Pay.
4 Contact Stax support with the Merchant ID(s) needing Apple Pay activation and each payment domain URL (e.g. https://pay.example.com) — Stax's Partner Success team completes the backend activation.
Tip: Google Pay needs none of this — no domain verification file is required; it's configured directly through Stax.js once the account is enabled.

3.2 File Access / 404 Errors on Domain Verification Links

The Issue: Accessing the domain verification file via test.msdata.services and msdata.co returned a 404 Not Found instead of the expected string of numbers.

The Root Cause: The verification file is extensionless. The hosting server runs IIS, which by default rejects or 404s extensionless files if no matching MIME type is configured.

The Resolution: Alvin identified the gap and added a MIME type mapping for extensionless files in the IIS configuration. Once IIS could correctly serve the extensionless file, both endpoints became accessible.

Note: If a future domain verification (Apple Pay or otherwise) 404s on an IIS-hosted domain, check the extensionless MIME mapping first — this is the same failure mode.

3.3 Live vs. Test Gateway Environment Mix-up

The Issue: There was confusion over where verification and testing should actually take place.

The Resolution: Stax Activations added the live gateway to the sandbox environment. Going forward, the team stopped using test cards and switched to live cards for verification and validation on the live server.

3.4 Verification of Multiple Domains

The Issue: Initially only the test domain (test.msdata.services) was verified, but both staging and production domains needed Apple Pay enabled.

The Resolution: After test.msdata.services was successfully verified, Alvin requested verification of msdata.co. Joseph Cerilli (Manager, Customer Success at Stax) manually validated and activated msdata.co for Apple Pay as well.

4. Google Pay & Stax.js Notes

From the same Stax documentation, for reference if Google Pay is enabled alongside Apple Pay:

  • No domain verification file is required for Google Pay — it's enabled directly through Stax.js once the merchant account is turned on.
  • Stax.js expects container <div>s with the IDs pay-with-apple and pay-with-google by default for rendering the buttons.
  • The transaction amount must be set before the buttons render, via the Stax.js configuration object or StaxJs.setPrice(string).
Note (Key Limitations): Digital wallet transactions (Apple Pay / Google Pay) through Stax cannot be surcharged, since tokenization prevents distinguishing credit vs. debit. They are also non-recurring, card-not-present only (aside from card-present semi-integrated terminals without surcharging), and Stax does not store the payment method for future use.
