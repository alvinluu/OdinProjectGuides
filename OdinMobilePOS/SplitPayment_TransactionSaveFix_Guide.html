Split Payment: Success HUD Without a Saved Transaction

Issue Resolution — Odin Mobile POS — Odin Inc.
Last Updated: September 18, 2026

At a glance: During a split payment the operator could see the green success HUD while the cart was not saved as a transaction. Root cause: success was reported independently of the save result. Fixed by only showing success once saveCartToTransaction confirms it actually saved. Fixed in commit 420ca8c7 (branch 2.0.40).

1. Symptom

During a split payment, the operator sees the green success progress HUD, but the cart is not saved to the transaction — no local transact rows are recorded. Because the sale looks like it went through, the discrepancy is usually only caught later during reconciliation.

2. Root Cause

The success indication was decoupled from the actual save result.

How success is signaled

The split's success HUD is driven by the widget's status flag. On close, SplitVC calls delegate?.closeSplit(status), and FirstView.closeSplit(status) shows MBProgressHUDHelper.showProgressSaleStatus(status, …). In SplitVC.performCompleteSale, status was set unconditionally: 

// before
status = true
closingSale = false
closeSelfWithAnimation()

When the save silently does nothing

Transaction.saveCartToTransaction can complete without saving anything, returning an empty array in two cases:

CaseLocationResult
Empty cart Transaction.swift:323 if itemArray.isEmpty { completionBlock([]); return } — no rows, no error
Invalid / unknown paycode Transaction.swift:453 Builds rows, detects payment contains "ERROR:", then deletes everything it just created and shows its own alert — leaving an empty result

Because performCompleteSale never inspected the returned array, either case still flipped status = true and showed the success HUD. The same "declare success regardless of the save" pattern also existed in several adjacent completion closures that hardcoded success or set status = true before the save: WidgetPatronBaseVC.SaveCartToTransaction, and the .EventApp / .Associated cases in PatronVC and PinVC.

3. What We Ruled Out

Ruled out: “The local save is deferred behind the network upload and lost if the upload fails.” On the success path, the local persist (completeSaving() → CoreDataService().save(moc)) is run inside the upload's completion only when Setting.shared.isAutoUploadPendingTran == false (Transaction.swift:506–509). In the current build this setting is always true, so the persist runs synchronously and is not gated on the network. So this was not the cause. It remains a latent fragility if that setting is ever turned off — see Follow-ups.

4. The Fix

Only signal success once saveCartToTransaction reports it actually persisted rows. If the returned array is empty, show a clear “Sale Not Saved” alert, keep the widget open, and do not show a success HUD.

SplitVC.performCompleteSale — guard added before the upload/close/success block:

guard !transArray.isEmpty else {
    status = false
    closingSale = false
    Alert().showSimpleAlert(
        "Sale Not Saved",
        message: "The transaction didn't save to this device. Please try again.",
        sourceView: self)
    return
}

The same guard was added to the adjacent flows so the guarantee holds beyond the split screen:

  • WidgetPatronBaseVC.SaveCartToTransaction — success only when trans is non-empty.
  • PatronVC .EventApp / .Associated — status = !trans.isEmpty, set inside the completion.
  • PinVC .EventApp — same.
Why this is safe for good sales: a real charge produces a non-empty transArray, so the guard passes and the flow is identical to before. Behavior only changes on an empty/failed save — exactly the case being fixed. WidgetPatronBaseVC.completeCartTransaction (the main patron charge) already checked if transArray.count == 0, so it was left unchanged.

6. How to Verify

1 Force an empty/failed save in a split — e.g. an account whose resolved paycode is invalid, or an empty cart reaching completion.
2 Confirm you get the “Sale Not Saved” alert and no success HUD, and the split stays open to retry.
3 Confirm a normal split still shows the success HUD and closes as before.

7. Follow-ups (Not Fixed Here)

  • Open Mainline single-patron charge still unguarded. FirstView.completeCartTransaction (FirstView.swift:248) and its private saveCartToTransaction sibling still show showProgressSaleStatus(true, …) in a { _ in … } closure, regardless of the save result. The most common (non-split) charge path is not yet protected by this guard.
  • Open splitOverrideApproved not reset in the new guard. The “Sale Not Saved” early-return doesn't reset the flag. It's masked in practice because processSplitSales(nil) resets it on each Process press, but it should be reset in the guard for correctness.
  • Watch Async-completion assumption. The !transArray.isEmpty guard assumes saveCartToTransaction completes synchronously (true while isAutoUploadPendingTran == true). If that setting is ever disabled, the guard would read an empty array for a single-entry split and falsely report “Sale Not Saved.”
